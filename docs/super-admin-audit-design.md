# Super Admin, users, and activity logs: implementation assessment

**Stage 14F.1: planning only.** The owner requested the permission matrix below. The implementation choices and outstanding decisions are recommendations for review, not existing functionality or authorization to implement it.

## Current implementation and gaps

- `roles.code` is text constrained to `admin` and `assistant_admin`; `users.role_code` references it. Users have a normalized unique login, display name, Argon2id password hash and `is_enabled`. There is no user-management HTTP API, UI, password-reset operation, or account enable/disable operation. The interactive `bootstrap-admin` CLI creates only the first Admin, refuses if any Admin already exists, uses a transaction-level advisory lock and records `first_admin_provisioned`. It is not a recovery mechanism.
- `auth.py` checks enabled state and the two allowed roles at login and session validation; `require_admin`, `auth_http.py`'s `admin_actor`, and `business_http.py` restrict CSV import and Received reversal. `orders.py` rechecks stored users with separate routine and Admin sets, `employee_imports.py` independently checks Admin, and `reports.py` checks both routine roles. `business_services.py` uses the order authorization helper. These checks must all change together. There is no existing user-management permission to remove from Admin: access does not exist yet.
- The frontend role union and checks live in `apps/web/src/lib/api.ts`, `meal.ts`, `pending-edit.ts`, and `employees.ts`; `app-navigation.tsx` displays a two-role label. Current destinations are Orders, Menu, Customers and Reports. These controls cannot enforce authorization by themselves.
- Sessions store a digest of an opaque token and a separate CSRF token. Validation checks the current stored user and role; disabling a user invalidates access on the next check, while a direct role change changes effective privileges on the next check. There is no account-management operation that explicitly revokes sessions. Future role changes, disabling and password resets must revoke them atomically. Retain existing HTTPS/development cookie profiles, exact Origin checks, CSRF, generic login failures, rate guard and no-store responses. The demo password minimum is 8 characters, nonblank, with a maximum of 1,024 UTF-8 bytes; Argon2id remains mandatory, with longer passwords recommended for production.
- `audit_events` stores a user FK, timezone-aware `occurred_at`, action, entity type/key, JSON before/after and optional reason. `receipt_events` links transitions to audits and retains correction code, label snapshot and explanation. Triggers reject update/delete on audit and receipt history. The actor's current display name can be joined, but there is no historical display-name snapshot; label it as current rather than claiming it is historical. Display timestamps with an explicit timezone, retaining the UTC instant. Audit writes for mutations are generally transactional; import failure history has a separate recovery transaction.
- Recorded actions found in source: `order_created`, `order_edited`, `received_marked`, `received_reversed`; `menu_created`, `menu_date_assigned`; `dish_created`, `dish_updated`, `dish_deactivated`, `dish_deleted`; `visitor_created`, `visitor_updated`, `visitor_deleted`; `employee_import_inserted`, `employee_import_updated`, `employee_import_completed`, `employee_import_failed`; `first_admin_provisioned`, `auth_login`, `auth_logout`. Successful login/logout are recorded; failed attempts, all reads, expiry, and future account actions are not established audit events. Uploads rejected before an import job exists need not have an import event. Do not fabricate missing history.
- Audit payloads can contain employee identifiers and imported fields, order customer snapshots, request and allocation details, visitor names, and free-text reasons. Existing authentication events contain a session record ID, not the secret token. Never expose raw JSON indiscriminately; historical records cannot be assumed safe just because new writes are sanitized.

Resolve that documentation discrepancy before implementation.

## Provisioning and account lifecycle

Recommend an interactive local `bootstrap-super-admin` CLI, extending `auth_cli.py` and `auth.py`, with hidden password input and confirmation, no password arguments or secrets in logs. Require an explicitly configured database, display a nonsecret database identity and require the operator to verify it before proceeding; never print the URL or credentials. Use an advisory transaction lock shared by all Super Admin creation/demotion/disable paths and refuse bootstrap if any Super Admin exists, even disabled. Create the individual account and an audit event atomically; use the new account as actor for local bootstrap and explicitly mark its local-bootstrap source. Preserve all existing accounts and data. Repeated or concurrent invocations must not create additional bootstrap accounts.

An optional separately reviewed local promotion procedure could identify an existing Admin by exact stable ID, verify the intended instance and target, explicitly confirm the change, lock the target and Super Admin guard, revoke its sessions and atomically audit before/after role plus local operator attribution limitations. It must never silently promote the first Admin. Whether promotion is permitted and how to attest the human operator are owner decisions; do not claim the target's identity proves who ran a local CLI. Recovery from a lost last Super Admin requires a separately approved, documented local procedure; do not bypass the lockout protection.

Only Super Admin may list/search accounts by login or display name, create Admin/Assistant Admin, enable or disable, change between those two roles, or reset passwords. Recommend Super Admin creation and promotion remain CLI-only to limit privilege escalation. Do not expose account deletion: retain identifiers for audit references. Disabling, role change or password reset locks affected users in stable order, revokes all affected sessions in the same transaction, writes a minimal audit and forces reauthentication; no secret or hash is returned in user responses or audit. Re-enabling does not revive old sessions. Require current target version/state to reject stale edits, and serialize last-active-Super-Admin checks; reject disable/demotion of the last active Super Admin even under concurrent requests. Prevent self-promotion and privilege escalation regardless of submitted role. Self-disable or self-role changes, if ever allowed, must use the same guard and end the session; recommend disallowing them initially. Maintain existing user-before-session lock order.

For password reset, recommend an authenticated Super Admin sets a new password through a protected, non-caching form over the existing secure transport; no email or default password. Validate via the existing password policy, use Argon2id, clear the input, never log request bodies, and revoke sessions atomically. The owner must approve how the individual receives the new secret and whether a forced-change feature is required; do not claim an unimplemented forced-change mechanism. This is an administrative reset, not identity verification of the recipient.

## Activity Logs: safe read design

Use the existing `audit_events` as the source and left-join `receipt_events` for transition metadata. Do not union import-row data into fabricated events. Add Super Admin-only read endpoints with bounded server-side pagination, inclusive date filters with an explicit operational timezone converted to timestamp bounds, actor ID, action, and exact entity type/reference filters. Sort by `(occurred_at DESC, id DESC)`; recommend a cursor carrying both values plus filter binding to avoid duplicates during concurrent inserts. Validate limits, dates and cursor, and expose a next cursor. Event detail by ID uses the same authorization and safe projection. New records may appear before the cursor on refresh; the list is not a frozen snapshot.

Return event ID, instant, actor ID and current display label, action, entity type/reference, and a deliberately allowlisted summary. For detail, explicitly map safe fields per action, including relevant status changes, reason label and limited explanation where approved; unknown actions receive only neutral metadata, never raw payload. In particular suppress passwords, hashes, session IDs/tokens, CSRF tokens, raw CSV and unnecessary employee identifiers/names, mask or suppress sensitive entity references such as employee numbers, and escape all text in the UI. Treat free-text explanations as potentially sensitive; decide whether to show them and to whom before enabling that detail. This projection must cover old events too. Do not fetch or expose unrestricted historical JSON to the browser. Audit viewing is read-only; DB append-only triggers protect against ordinary update/delete, not a database owner disabling triggers or altering storage. Restrict runtime DB grants and protect backups and operational access.

## Proposed schema and API

A new Alembic revision is required: change `ck_roles_code_allowed` to include `super_admin` and insert its reference row, retaining existing users and frozen migrations. Update the SQLAlchemy constraint in `apps/api/src/asi_meal_api/db/models.py`. A downgrade must refuse if Super Admin users exist, rather than delete or silently demote them. No additional user column is essential if stale updates use expected current fields with row locks; a version column is an alternative if needed. Session versioning is unnecessary if revocation and user changes are atomic and checks remain server-side.

The existing entity/time audit index does not efficiently support every global newest-first query. Propose an `(occurred_at DESC, id DESC)` index in the new revision; consider actor/action composite indexes only after realistic query plans show a need. Existing audit/receipt schemas support the read view; future account events use the existing audit table and minimal allowlisted before/after fields. Do not rewrite historical audits or snapshots. Provisioning attribution and any new fields require explicit review before migration.

Suggested contracts, subject to review:

- `GET /api/users?q=&limit=&cursor=` returns bounded account ID, login, display name, role, enabled state and pagination metadata; no credentials.
- `POST /api/users` accepts login, display name, Admin/Assistant role and password; `PATCH /api/users/{id}` accepts explicitly allowed fields and expected current state; `POST /api/users/{id}/password` accepts a new password and expected state. Unknown fields, Super Admin assignment and untrusted actor IDs are rejected. Separate explicit enable/disable operations may be clearer than PATCH if contract review prefers them.
- `GET /api/activity` supports bounded cursor and filters; `GET /api/activity/{id}` returns an allowlisted detail. Every route derives the actor from the authenticated session; unsafe requests require trusted Origin and CSRF. Return generic conflict or validation errors without secrets; restrict list/search to Super Admin to reduce enumeration.

Audit each successful account creation, status/role change and reset with actor, target, UTC time and safe before/after metadata in the same transaction. No-op changes need not create events; failures must not leave partial changes. Never store passwords, hashes, session tokens or arbitrary submitted request bodies in the audit. Existing session and authorization checks must continue to fail closed for unknown roles. Rate-limit sensitive endpoints appropriately within the existing bounded guard approach; multi-worker deployment still needs separately reviewed shared abuse controls, and throttling must not replace authorization.

## UX and responsive behavior

Add Users and Activity Logs only to Super Admin navigation, keeping Orders, Menu, Customers and Reports for all three roles. Use existing sidebar at desktop and accessible drawer below 1024px, current local Cardo/Open Sans and ASI tokens. Preserve active text/marker, skip link, focus entry and return, Escape, keyboard operation and visible focus. Users gets compact search, role/status columns and clearly labeled actions with confirmations and stale/error states. Activity Logs gets compact filters, newest-first list and a read-only detail panel, showing explicit timezone and current actor label. Use accessible names for icon controls and text event labels. At 1440, 1366, 1024, 768, 390 and 375px, use responsive cards or keyboard-scrollable table regions, wrap controls and avoid page-level overflow. No oversized dashboard.

## Implementation sequence and acceptance

1. **Role and authorization foundation.** Likely files: `db/models.py`, a new `alembic/versions` revision, `auth.py`, `auth_http.py`, `orders.py`, `employee_imports.py`, `reports.py`, relevant frontend role helpers and tests. Migrate a verified disposable PostgreSQL instance; test upgrade from existing data, no promotion, safe downgrade refusal, unknown-role denial, every matrix cell through HTTP and services, current session behavior, and preserved Admin/Assistant workflows. Existing deployment must apply the reviewed migration and restart API; frontend needs a rebuild/restart when role changes are shipped. Coordinate rollout to avoid a Super Admin role being rejected by old processes.
2. **Bootstrap and account services.** Likely `auth.py`, `auth_cli.py`, new focused account service/schema/HTTP modules, `main.py`, auth and HTTP tests, runbook. Implement the agreed bootstrap/promotion decision and proposed user contracts. Test concurrent first provisioning, duplicate login, last-active guard under concurrency, stale writes, session revocation and in-flight locking, atomic rollback on audit failure, input/secret handling, and role/Origin/CSRF denial. No production data.
3. **Audit coverage and read API.** Likely a focused audit service/HTTP schema and `main.py`, existing account audit writes and `test_business_http.py`/new tests; migration index as above. Test deterministic cursor under tied timestamps and concurrent inserts, filters, invalid input, safe rendering of synthetic legacy payloads, receipt reasons, missing historical events, role denial, and append-only and atomic-write invariants. Confirm no credential, token, raw CSV or unnecessary personal details leak.
4. **Frontend workspaces.** Likely `app-navigation.tsx`, `meal-app.tsx`, `lib/api.ts`, new Users and Activity Logs components, `globals.css`, existing role helpers and focused frontend tests. Exercise all account and audit states, accessible controls and errors; test desktop and mobile widths above in a real browser using synthetic accounts. Verify backend denial independently of hidden navigation.
5. **Full regression.** Run frontend lint, tests, TypeScript and production build; backend auth, business HTTP, order, import, reports and migration tests against the established isolated disposable PostgreSQL harness. Check session expiry, Origin/CSRF, old role permissions, audit privacy, concurrent changes and rollback, as well as keyboard focus and responsive layout. Document results and any deployment/restart steps. Optional later enhancements include additional indexes only when measured; no email reset, external identity platform, audit export or settings UI is required here.

## Decisions before implementation

**Blocking:** approve first-Super-Admin creation versus explicit promotion, operator attribution and instance-verification procedure; approve initial account role-change and self-management limits and last-Super-Admin recovery; approve secure password handoff and whether forced change is required; approve audit detail allowlist, especially correction explanations and employee-related values; reconcile the older Assistant reversal wording with the owner matrix. Review role and migration rollout before deployment.

**Can remain open if excluded from the first release:** UI creation of additional Super Admins, historical actor display-name snapshots, audit retention policy and additional query indexes. Existing audit gaps remain visible and must not be represented as complete history. Production readiness, deployment-wide throttling and backup/recovery controls remain separate operational work.
